# Skillo AI — v1.1 Limitations

> **Purpose**: Honest documentation of the current system's limitations before Phase 2 begins.
> This document serves as the bridge from v1.1 to v2 — every limitation here maps to a concrete v2 objective.
> Do not delete this file when v2 starts. It is a permanent historical record.

---

## 1. ML & Semantic Matching Limitations

### 1.1 TF-IDF has no contextual understanding

The character n-gram TF-IDF vectorizer represents text as weighted character frequency bags. It has no sense of meaning, context, or semantic relationships between words. Two concepts can be described using entirely different words yet mean the same thing, and the model will fail to recognize the equivalence.

**Example failure cases:**
- `"FastAPI"` vs `"REST API development in Python"` — these describe highly overlapping skills but have low character overlap.
- `"Containerization"` vs `"Docker"` — a learner who says "I know containerization" won't get credit for Docker.
- `"LangChain"` vs `"LLM application framework"` — no connection visible at the character level.

**Impact:** The system may miss real skill matches (false gaps) or produce unexpected match scores for semantically related but textually different inputs.

### 1.2 A single global threshold does not generalize

The cosine similarity threshold `τ = 0.60` is a fixed global value. This means the same cutoff is applied to a highly technical domain (e.g., `Kubernetes` vs `container orchestration`) and a general domain (e.g., `Python (basic)` vs `Python (advanced)`).

Different skill categories may naturally have different similarity distributions. A fixed threshold is a heuristic, not a calibrated decision boundary.

**Impact:** The threshold may be too lenient for some skill pairs (false matches) and too strict for others (false gaps).

### 1.3 Skill similarity depends entirely on taxonomy description quality

The TF-IDF vectorizer is fitted on skill names and descriptions from `seed_skills.json`. If a skill description is short, generic, or uses unusual phrasing, its vector representation will be poor and similarity scores will be unreliable.

**Impact:** Skill matching quality is tied to manual curation quality. Two identically-important skills can produce very different similarity scores if their descriptions differ in length or vocabulary.

### 1.4 Learner skill inputs are self-reported and unverified

Learners manually select skills from a dropdown. There is no mechanism to verify the accuracy of self-reported skill levels. A learner who selects `Python (advanced)` is taken at face value.

**Impact:** Roadmaps are only as accurate as the learner's honest self-assessment. Overconfident learners will get shorter, potentially incorrect roadmaps.

### 1.5 Goal classification is constrained to the curated 6-role taxonomy

The goal parser can only recognize one of the 6 supported career roles. Any query that doesn't map well to these roles (e.g., `"I want to work in cybersecurity"` or `"I want to become a data engineer"`) will either get a low-confidence label or be assigned the closest matching role incorrectly.

**Impact:** The system is not general-purpose. It cannot gracefully handle career goals outside its taxonomy.

## 2. Recommendation & Roadmap Limitations

### 2.1 Resource selection is not ranked or personalized

For each skill gap, the system selects the **first non-remedial resource** from `seed_resources.json`. There is no ranking model, no difficulty calibration, no learner-history-aware selection, and no consideration of resource quality or learner level.

**Impact:** Two learners with very different backgrounds get identical resources for the same skill.

### 2.2 Adaptation is deterministic, not learned

The adaptive feedback loop uses fixed score thresholds:
- Score `< 50%` → insert remedial step
- Score `≥ 90%` → flag downstream steps as skippable
- Score `50–89%` → mark complete and advance

These rules were designed as heuristics. They were not derived from learner outcome data, cohort performance analysis, or any form of machine learning.

**Impact:** The adaptation policy is brittle. It does not improve with usage. It cannot learn that a particular learner style benefits from a different policy.

### 2.3 Roadmap ordering is purely prerequisite-driven, not relevance-ranked

The prerequisite graph enforces ordering constraints (skill A before skill B), but within those constraints, there is no ranking of skills by importance, difficulty, or learner-specific relevance. Skills are ordered topologically — the "right" order structurally, but not necessarily the most effective pedagogical order.

**Impact:** Two equally important skills at the same DAG depth are ordered arbitrarily. There is no signal for which one a learner should tackle first when neither strictly depends on the other.

### 2.4 Taxonomy coverage is static and manually maintained

The skill and role taxonomy covers 6 roles and 36 skills. Adding a new career track, skill, or prerequisite relationship requires manual data entry by a developer and a reseeding operation.

**Impact:** The system cannot grow or adapt to new technologies or career domains without human intervention.

## 3. Data Limitations

### 3.1 Taxonomy is small relative to real-world skill diversity

Real-world software engineering involves hundreds of frameworks, tools, platforms, and programming languages. The 36-skill taxonomy is a curated subset. Learners who want to learn technologies not in the taxonomy (e.g., `Rust`, `Go`, `Kafka`, `gRPC`) will not receive tailored guidance.

### 3.2 No real learner data was used to validate the taxonomy

The skill descriptions, prerequisite relationships, and role definitions were crafted manually without validation from real learner outcomes. The "which skill depends on which" relationships are based on engineering domain knowledge, not empirical evidence from learner trajectories.

**Impact:** The prerequisite graph represents an opinionated view of skill dependencies, not an empirically validated one.

### 3.3 Evaluation datasets were curated, not collected from real users

The goal classification benchmark (12 queries), skill gap test cases, and failure case dataset were created manually by the development team. They are not a random sample from real user behavior.

**Impact:** Metrics computed on these datasets may be optimistic. Real-world performance on diverse user inputs is unknown.

## 4. LLM & Explanation Limitations

### 4.1 Explanations depend on external LLM availability

The full XAI experience (enriched natural-language rationales) requires an active Gemini API key. Without it, the system falls back to template-based explanations derived directly from graph topology.

**Impact:** Deployed instances without API keys provide simpler, less fluent explanations.

### 4.2 LLM explanations are not guaranteed to be accurate

Even with grounding from graph facts, the Gemini model may produce explanations that sound plausible but contain subtle inaccuracies. The grounding mechanism reduces but does not eliminate hallucination risk.

**Impact:** Users who trust LLM-generated explanations implicitly may occasionally receive misleading rationales.

### 4.3 The LLM has no role in the core recommendation

This is a deliberate design choice (and a strength), but it also means the recommendation quality ceiling is bounded by the TF-IDF + graph architecture. The LLM cannot compensate for gaps in the matching or ordering logic.

---

## 5. Infrastructure & Operational Limitations

### 5.1 No model versioning

There is no mechanism to version the TF-IDF vectorizer or its fitted vocabulary. If the taxonomy changes (new skills added, descriptions updated), the vectorizer is rebuilt at startup from the current state. There is no rollback mechanism.

**Impact:** Taxonomy updates can change recommendation behavior unpredictably.

### 5.2 No automated evaluation pipeline

The evaluation benchmarks exist as static files. There is no automated CI/CD job that re-runs the benchmark suite when taxonomy or model code changes.

**Impact:** Regressions in recommendation quality could go undetected.

### 5.3 Single-node architecture with no request-level observability

There is no request tracing, structured latency logging, or per-endpoint performance monitoring. Performance is measured only via manual benchmark scripts.

**Impact:** Production performance issues are difficult to diagnose.
